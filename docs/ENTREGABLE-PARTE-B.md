## 2. Cierre de la auditoría

```
Top 3 carencias que más duelen:
1. No hay guía operacional ni pipeline CI/CD (no Dockerfile, no despliegue, no runbooks). Si el proyecto tuviera que salir de "localhost" hoy, no hay ni un documento que diga cómo, y tampoco hay tests automatizados que den confianza para hacerlo. Es el hueco que más bloquea "de MVP a producción".
2. Divergencia real spec↔código en OpenSpec (`GET /api/v1/users/active` documentado y no implementado, con el dato `last_seen_at` ya listo). Es el tipo de discrepancia que, si no se detecta a tiempo, hace que alguien confíe en la spec para integrarse y descubra el fallo en producción — mina la utilidad de OpenSpec como fuente de verdad.
3. Cero ADRs y arquitectura sin documento propio ni diagrama. Decisiones con alternativas reales (SQLite, access tokens vs. JWT/sesiones, VineJS) están tomadas pero no justificadas en ningún sitio; una persona nueva no puede saber "por qué así y no de otra forma" sin preguntar directamente al equipo — justo lo que el README sí evita para el arranque, pero la arquitectura no.
```

```
Top 3 cosas que ya están bien (no tocar en la sesión):
1. README raíz + backend/README.md: onboarding de cero a servidor corriendo, sin ambigüedad, con comandos copy-paste correctos (incluye el paso fácil de olvidar, `node ace generate:key`). No romper este flujo.
2. CLAUDE.md como fuente de convenciones: es corto, concreto, y con una sección "No hacer" que previene los errores típicos (lógica en rutas, exponer modelos Lucid, commitear secretos). Cualquier copiloto de IA que lo lea sabe cómo tocar el backend sin salirse del patrón.
3. Specs de OpenSpec para `authentication` y `users` (la parte que sí está implementada): documentan bien los escenarios de éxito y error con sus códigos HTTP reales, mejor que la tabla plana del README. Sirven de base sólida para seguir especificando el resto de la API con el mismo formato.
```

## 3. Exploración rápida de tres formatos de documentación (Paso 7)

- **Diagrama C4 (c4model.com):** de un vistazo separa 4 niveles de zoom (Context → Container → Component → Code), así que responde "¿qué es el sistema desde fuera?" y "¿cómo está hecho por dentro?" con el mismo lenguaje visual — algo que unas notas sueltas en Markdown no dan porque no fuerzan una jerarquía de abstracción consistente entre lectores.
- **ADR (`joelparkerhenderson/architecture-decision-record`):** cada decisión es un documento corto, fechado e inmutable con contexto, decisión y consecuencias — a diferencia de una nota suelta, dejas rastro de **qué alternativas se descartaron y por qué**, no solo la decisión final, así que la decisión es auditable meses después sin tener que preguntarle a quien la tomó.
- **Especificación OpenAPI pública (ej. GitHub/Stripe):** al ser un contrato machine-readable (YAML/JSON con schemas tipados), permite generar clientes, validar peticiones y navegar la API en un explorador interactivo (Swagger UI) sin leer una sola línea de código — algo que ninguna tabla Markdown, por bien escrita que esté, puede ofrecer.
